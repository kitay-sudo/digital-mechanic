## Что сделано за 48 часов и что нет

Сделано. «Цифровой механик» — веб-приложение с AI-агентом для механика автопарка. Механик выбирает машину и проверку, агент получает результат от Mock ML и объясняет его простыми словами. Норма: работа продолжается. Отклонение: тип неисправности, риск, проверки и нормативы из руководства на двигатель этой машины, с документом, страницей PDF и дословной цитатой. Сбой записи: выводов нет, нужна повторная запись. На вопросы агент отвечает только по шести руководствам заказчика (1743 страницы). Если ответа нет, он прямо об этом говорит. Заявку на дефектовку агент собирает по команде механика: работы и запчасти из руководства, приоритет с основанием. В ТОиР она уходит только после того, как механик подтвердит состав.

Дополнительные задачи B1–B3 сделаны. B1 — память по машине: прошлые проверки, заявки и история чата. Механик подписывается фамилией, его вопросы и отметки «сделано» видны сменщику; вернувшись к машине через часы или месяцы, механик и агент видят, на чём остановились, а повтор неисправности после ремонта код отмечает сам. B2 — график anomaly_score с тенденцией. B3 — сводка главного механика по парку: норма, требует внимания, карантин.

По кик-оффу и Q&A с заказчиком сделано: голосовой ввод (запись видна по кнопке микрофона), фото узла на вход (камера или галерея), крупный текст, подача ответа для опытного механика и для новичка, шаги проверки с отметкой «сделано», постоянная кнопка «Создать заявку», которая объясняет, почему заявку пока нельзя создать, «Сообщить о проблеме» у каждого ответа и «Написать администратору», согласие на обработку данных. Работает в браузере на телефоне и компьютере.

Для администратора и интеграции: роли и вход (механик — фамилия в списке и PIN из четырёх цифр, администратор — логин и пароль), экран «Механики» с ФИО, возрастом, шрифтом и подачей; журнал для большого парка со страницами, поиском, фильтрами, статусами разбора «новый / в работе / разобрано» и склейкой повторов; сводка администратору раз в день; экран «Смена» с метриками пилота; выгрузка расчёта стоимости в xlsx; API для внешних систем `/api/v1` с документацией `/api/docs`: машины из учётной системы парка, веб-хук «проверка готова», механики, настройки подключений, вопрос агенту.

## Подход и архитектура

Главный принцип: модель может ошибиться, поэтому всё, от чего зависит безопасность и правильность, проверяет код.

Агент сам выбирает инструмент по смыслу сообщения механика, цепочки if-else в сценарии нет. Инструментов шесть:
- get_diagnosis — результат проверки из Mock ML;
- get_vehicle_history — прошлые проверки и заявки машины;
- search_manuals — поиск только по руководствам двигателя этой машины;
- read_manual_page — страница целиком;
- prepare_ticket — черновик заявки с проверкой ссылок;
- submit_ticket — отправка в Mock ТОиР после подтверждения механика.

Модель подключена через один слой, агент не знает, какая модель отвечает. Ответ ограничен JSON-схемой в порядке из ТЗ: наблюдения, гипотезы, проверки, возможный ремонт, ограничения.

Что проверяет код:
- каждая ссылка содержит дословную цитату, и код сверяет её со страницей PDF; не нашлась — пункт отбрасывается;
- числа-нормативы должны стоять на процитированной странице, числа в гипотезах запрещены;
- норматив от другого двигателя недоступен: поиск ограничен руководствами этой машины;
- сбой записи или качество bad: выводов и заявки нет;
- warning: предупреждение показывается всегда, заявка возможна только после явного согласия механика;
- порог уверенности 0,50: ниже него заявки нет, нужна повторная проверка;
- дизельная неисправность у бензинового двигателя считается ошибкой модели диагностики: карточка машины важнее, заявки нет;
- подложенные в описание признаков команды отбрасываются до модели и до экрана, механика ими не отвлекаем, администратор видит такие случаи в журнале;
- если источники расходятся, механик видит все формулировки со страницами и один пункт «Как поступить»: решение, согласованное с технической службой, или совет работать по более осторожной формулировке и уточнить у производителя;
- если инструкции в руководстве нет, механик получает честный отказ и рекомендацию на дефектовку, а администратор видит этот случай в журнале со статусом разбора и получает его в сводке за день;
- фото узла агент описывает с пометкой «По фото», диагноз только по снимку не ставит, нормативы берёт из руководства.

Приоритет заявки задаёт код. В основе — базовая критичность типа неисправности: машина не готова к рейсу и безопасность (тормоза, коробка) — высокий приоритет, дальше по стоимости ремонта. К ней добавляется поправка не больше одной ступени по оценке отклонения и её росту от проверки к проверке. При помехах или уверенности ниже 0,60 приоритет не выше среднего. Основание показано механику, окончательный выбор за ним, изменение записывается.

База знаний: PDF читаются постранично, страницы без текстового слоя распознаются Tesseract. Каждый фрагмент привязан к одной странице. Поиск — SQLite FTS5 с русским стеммером и ранжированием BM25, оглавления в выдачу не попадают. Адреса Mock ML и Mock ТОиР задаются в .env, для рабочих сервисов меняются только они.

## Стек и модели

Модель на стенде: Claude Haiku 5.5 (Anthropic) через ProxyAPI — доступ из России, оплата в рублях. Она же смотрит фото узла. Распознавание речи: gpt-4o-mini-transcribe через тот же ProxyAPI, около 1–2 с на фразу. По прогону 27.11:
- 21 из 21 контрольного вопроса;
- около 1,80 ₽ без НДС на сценарий от результата диагностики до ответа, отдельный вопрос около 0,9 ₽;
- ответ на вопрос от 4 до 22 с, медиана 9 с.

Модель меняется в .env без правки кода. Ещё два варианта:
- локальная модель в контуре заказчика через сервер с форматом OpenAI (Ollama, vLLM); проверена на Qwen2.5 7B, 14 из 21 контрольного вопроса;
- российское облако Yandex AI Studio; настройки готовы, но через этот вариант агент ещё не запускался.

Режим заглушки модели работает без ключа.

Сервер: Python 3.12, FastAPI, Uvicorn, Pydantic, httpx, Anthropic Python SDK, PyMuPDF (AGPL-3.0), Tesseract OCR с русской моделью, SQLite FTS5, snowballstemmer, openpyxl.

Интерфейс: Next.js, React, TypeScript, шрифты IBM Plex (@fontsource), иконки Tabler. Голос распознаёт сервер: gpt-4o-mini-transcribe через ProxyAPI, в контуре заказчика — свой Whisper по протоколу OpenAI; без настройки — распознавание браузера.

Компоненты третьих лиц: заглушки Mock ML и Mock ТОиР и синтетические данные парка от заказчика, шесть PDF руководств производителей. Материалы заказчика в репозиторий не входят, на стенде скачиваются при развёртывании.

Сделано до спринта как проектные материалы, без кода: замысел решения (docs/design.md), питч (docs/pitch.md) и статичный макет интерфейса (docs/mockups/digital-mechanic.html). Весь код сервера, агента и интерфейса написан в спринте. Разработка велась с ИИ-ассистентом Claude Code.

## Запуск и поставка

Поставка: один docker compose из четырёх сервисов — интерфейс, сервер с агентом, Mock ML, Mock ТОиР. Нужны Docker и ссылка на материалы задачи.

Запуск за пять шагов, подробно в README:
1. Скопировать .env.example в .env и вписать MATERIALS_URL, ключ модели, пароль администратора (ADMIN_PASSWORD) и ключ подписи (SECRET_KEY).
2. docker compose build.
3. Скачать материалы и собрать индекс: docker compose run --rm --no-deps backend uv run --no-dev python -m app.materials. PDF и данные заглушек скачиваются по ссылке, раскладываются и индексируются сами.
4. docker compose up -d.
5. Интерфейс на порту 3000.

Без ключа модели продукт запускается на заглушке модели: путь, правила и проверки работают.

Подключение к рабочим системам заказчика: адреса ML-сервиса и ТОиР меняются в .env (MOCK_ML_URL, MOCK_TOIR_URL) или на экране «Подключения» без перезапуска, модель — в .env (LLM_PROVIDER, адрес и ключ). Учётная система парка и ML-сервис подключаются через API `/api/v1` по ключу (docs/integration.md): машины, веб-хук «проверка готова», механики. Для контура заказчика с закрытыми данными модель ставится на его сервер. Требования к серверу и модели: docs/local-model.md.

Для механика: веб-приложение работает на ноутбуке в ремзоне и на телефоне в браузере. Механик входит одним касанием: фамилия в списке и PIN.

Проверка: 130 автотестов (cd backend && uv run pytest -q), быстрая проверка стенда без модели (uv run python -m eval.smoke), прогон контрольных вопросов (uv run python -m eval.run_eval ask) и сценариев защиты (uv run python -m eval.run_scenarios).
