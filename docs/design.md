Хакатон "ИИкузница", трек "Цифровой аватар". Документ описывает замысел. Код, конфигурации, промпты и поисковые индексы прототипа создаются только в спринте, с 10:00 26.11 до 10:00 28.11 МСК (п. 4.4 положения, организаторы это подтвердили).

ТЗ, заглушки, данные и ссылку на руководства выдают 26.11 на брифинге.

## 1. Исходные данные

- **Всё синтетическое.** Агент работает с результатом акустической проверки двигателя. OBD-телеметрии, пробега, истории ТО и аудиозаписей нет.
- **Парк: 50 машин, файл vehicles.json.** У каждой машины 3–5 проверок с датой и временем. Модель двигателя есть только в карточке машины, в ответе ML её нет.
- **ML-заглушка.** FastAPI со спецификацией OpenAPI, запускается локально. По номеру машины и номеру проверки отдаёт результат в JSON. Списка машин не отдаёт, он лежит в vehicles.json.
- **Ответ ML.** Статус проверки (норма, отклонение, сбой записи), код и название типа неисправности, оценка отклонения, уверенность модели, качество записи, текстовое описание признаков, версия модели. Типов неисправностей 14 (F01…F14), к ним есть справочник. Коды условные, в руководствах их нет.
- **ТОиР-заглушка.** Принимает заявку на дефектовку, проверяет формат и то, что проверка с таким номером есть у этой машины. Возвращает номер TKT-0001, TKT-0002 и так далее. Хранит заявки в памяти, после перезапуска нумерация начинается заново. Дубли не ловит, списка не отдаёт.
- **Модели.** Внешние API разрешены, отправлять в них фрагменты руководств и синтетические результаты можно. Закрытый контур и работа без интернета не нужны.
- **Интерфейс.** Веб-приложение с чатом: выбор машины, кнопка получения результата диагностики, диалог с агентом. Должно работать на смартфоне. Голос не обязателен.
- **Сдача (по Положению от 25.11).** Форма в личном кабинете до 10:00 28.11: ссылка на видео, открытый репозиторий с историей коммитов (оценивают последний коммит до 10:00 28.11), короткие ответы формы, URL стенда, ссылка на заполненный шаблон расчёта стоимости одного запроса. Одностраничника больше нет.
- **Стенд обязателен.** Это отменяет ответ от 20.11, что стенд не нужен. Работает с 10:00 28.11 до 23:59 3.12, на питче показываем решение вживую именно на нём. До 15.12 по запросу поднимаем за 24 часа. Заглушки проверены на Windows 11 и Python 3.10+, запуск по README тоже нужен.
- **Проверка.** Автоматического прогона нет. Жюри задаёт агенту контрольные вопросы по руководствам, часть заранее не раскрыта, и сверяет ссылки по PDF. Новых машин сверх 50 не будет, но среди них есть контрольные случаи (раздел 3).

Всего 6 PDF. У всех есть текстовый слой, но часть страниц состоит из картинок: чертежи и отдельные таблицы. Для них нужно распознавание. ## 2. Что требует задача и чем это закрываем

| № | Требование из задачи | Чем закрываем |
|---|---|---|
| 1 | Получить результат проверки двигателя от внешнего ML-сервиса | Механик выбирает машину и проверку, нажимает "Получить результат диагностики". Агент запрашивает заглушку по номерам машины и проверки, двигатель берёт из карточки машины |
| 2 | Объяснить отклонение, возможные причины и риски | Агент объясняет тип неисправности и признаки из ответа, показывает оценку, уверенность и качество записи. Предлагает приоритет и пишет, на чём он основан |
| 3 | Найти в руководствах процедуры, нормативы и рекомендации | Поиск только по руководствам двигателя этой машины. Каждый фрагмент привязан к документу и странице PDF |
| 4 | Отвечать на уточняющие вопросы с источником и страницей | Чат по проверке. Ссылка открывает страницу PDF с подсветкой нужного места |
| 5 | По подтверждению сформировать заявку на дефектовку для ТОиР | Только по команде механика. Он видит состав заявки и подтверждает именно его. Без работ и проверенных источников заявка не уходит |

## 3. Как это выглядит для механика

1. Открывает приложение на телефоне. Видит парк: 50 машин, поиск по номеру, у каждой статус последней проверки.
2. Выбирает машину. Видит модель, двигатель и историю проверок с датами. По умолчанию выбрана последняя проверка.
3. Нажимает "Получить результат диагностики". Агент запрашивает результат и разбирает его, шаги видны по ходу.
4. Дальше один из пяти исходов. Последние три жюри проверяет специально, такие случаи уже есть в данных:

| Результат проверки | Что делает агент | Заявка |
|---|---|---|
| Норма | Коротко сообщает, сравнивает с прошлыми проверками | Не предлагается |
| Отклонение | Объясняет, чем грозит, даёт порядок проверки со страницами PDF, предлагает приоритет с обоснованием | Можно оформить |
| Отклонение, но в руководстве на этот двигатель нет инструкции | Так и говорит, рекомендует дефектовку, данные другого двигателя не берёт. Если есть общая процедура осмотра узла, ссылается на неё со страницей | Только если нашлась общая процедура. Иначе не отправляется |
| Запись с помехами или сниженная уверенность | Предупреждает первой строкой, выводы осторожные, советует повторить запись | Можно, приоритет с поправкой на уверенность |
| Сбой записи или плохое качество | Диагноз не ставит, о двигателе выводов не делает, просит повторить запись | Нет |

5. Задаёт вопросы в чате. Ответ приходит со ссылкой на страницу PDF, по нажатию открывается страница с подсветкой. Если в руководстве ответа нет, агент так и говорит.
6. Пишет "оформи заявку". Агент собирает черновик, механик проверяет состав и подтверждает. Приходит номер TKT, приложение сохраняет его вместе с машиной, проверкой и временем.

Интерфейс делаем сначала под телефон. На компьютере две колонки: слева разбор и чат, справа страница руководства. В таком виде записываем видео. Голос делаем в конце спринта, если останется время: распознавание речи браузера.

## 4. Архитектура

```
vehicles.json ──► Справочник парка ──► карточка машины, двигатель, история проверок
                                              │
ML-заглушка ◄──── номер машины + проверки ── Агент ──► разбор, ответы со ссылками
 (FastAPI)                                    │
                                              │ поиск только по документам
6 PDF ──► Подготовка ──► Индекс ◄─────────────┘ двигателя этой машины
          текст по страницам,  точный + смысловой
          распознавание
          страниц-картинок
                                              │
                                     Черновик заявки
                                              │ подтверждение механика
                                              ▼
                                     ТОиР-заглушка ──► номер TKT

Журнал: шаги агента, токены, стоимость, время. Свои заявки по машинам.
```

Компоненты:

- **Справочник парка.** Читает vehicles.json: машина, модель, двигатель, история проверок. Здесь же таблица "двигатель → документы": 5 обозначений двигателей на 6 PDF.
- **Клиент ML-заглушки.** Запрашивает результат по номерам машины и проверки и приводит его к внутреннему виду. Формат меняется в одном месте.
- **Подготовка руководств.** Текст по страницам PDF. Страницы, где текста почти нет, рендерим в картинку и распознаём (Tesseract, русский язык). Таблицы нормативов держим целиком. Для каждой страницы храним картинку для просмотра. У каждого фрагмента храним документ, раздел, номер страницы PDF и координаты блока. По координатам просмотрщик подсвечивает нужное место и прокручивает к нему. Если координат нет, подсвечиваем всю таблицу или показываем страницу без подсветки.
- **Индекс.** Гибридный поиск: точный (обозначения деталей, моменты затяжки, номера пунктов) плюс смысловой (признаки своими словами). Жёсткий фильтр по документам двигателя машины.
- **Агент.** Многошаговый цикл с инструментами, раздел 5.
- **Клиент ТОиР-заглушки.** Перед отправкой сам проверяет обязательные поля, чтобы заглушка не вернула ошибку на демо.
- **Журнал и хранилище.** Шаги, вызовы модели, токены, стоимость и время по каждой проверке. Плюс собственный список отправленных заявок: заглушка его не хранит.

## 5. Агент

Инструменты:

- найти машину и получить её карточку с историей проверок;
- получить результат проверки из ML-заглушки;
- получить описание типа неисправности из справочника F01…F14;
- найти фрагменты в руководствах (только документы двигателя машины);
- открыть страницу PDF целиком: нужна для таблиц и соседнего контекста;
- получить отправленные заявки по машине;
- собрать черновик заявки;
- отправить заявку в ТОиР.

Как работает:

1. Кнопка "Получить результат диагностики" запускает агента. Дальше он сам: берёт результат, читает карточку машины и историю, по статусу и качеству записи выбирает ветку из раздела 3, делает несколько поисков по руководствам (узел, признаки, проверки, нормативы), открывает нужные страницы и собирает разбор.
2. Коды F01…F14 в руководствах не встречаются. Поэтому агент ищет по названию типа и описанию признаков из ответа ML, а не по коду.
3. В чате агент на каждый вопрос сам решает, что искать и какие страницы открыть.
4. По команде "оформи заявку" заполняет черновик из результата проверки, найденных процедур и диалога.

Логику приоритета заказчик не задал, предлагаем свою и показываем основание в интерфейсе. Пороги выставим по распределению значений в выданных данных, не наугад:

- **Высокий.** Отклонение с высокой оценкой при хорошей записи и уверенности. Или оценка по тому же типу растёт от проверки к проверке. Или руководство прямо связывает такой признак с риском отказа, тогда со ссылкой.
- **Средний.** Отклонение с умеренной оценкой. Или высокая оценка при сниженной уверенности либо помехах.
- **Низкий.** Пограничная оценка или низкая уверенность. Совет: повторная запись и осмотр.
- **Расхождение.** Если оценка высокая, а уверенность низкая, выше среднего не ставим, прямо пишем об этом механику и советуем повторить запись.

Основание показывается одной строкой, например: "Приоритет средний: оценка 0,72, уверенность ниже порога, запись с помехами, второе отклонение этого типа за месяц".

Правила, которые держит код, а не только инструкция модели:

1. **Только руководства этого двигателя.** Поиск не видит чужие PDF. Ссылка на документ другого двигателя отбрасывается.
2. **Каждая ссылка проверяется по странице.** Числа и ключевые слова из ответа должны быть в тексте указанной страницы PDF, включая распознанный текст. Если проверка не прошла, ответ не показываем: агент ищет заново или говорит, что данных нет.
3. **Сбой записи и плохое качество.** Для такой проверки диагноз и заявка выключены.
4. **Заявка только по подтверждению.** Уходит после нажатия механика и ровно в том составе, который он видел. Если состав изменился, нужно подтвердить заново.
5. **Проверка перед отправкой.** Работы не пустые. Источники не пустые и все прошли проверку из п. 2. Тип неисправности и номер проверки совпадают с ответом ML. Иначе кнопка неактивна и написано почему.
6. **Повторная отправка.** Если по этой проверке уже есть номер TKT, предупреждаем. ТЗ этого не требует, но сделать дёшево.
7. **Предупреждение о помехах и низкой уверенности** выводит интерфейс по полям ответа ML. От текста модели оно не зависит.

Память по машине: история проверок из vehicles.json, наши прошлые разборы и отправленные заявки. Если отклонение того же типа повторяется, агент это видит и учитывает в приоритете.

## 6. Заявка на дефектовку

Состав по ответам организаторов. Точные названия полей будут в ТЗ 26.11.

- машина;
- проверка;
- тип неисправности: код и название из ответа ML;
- диагноз;
- приоритет: низкий, средний или высокий;
- перечень работ, не может быть пустым;
- перечень запчастей, может быть пустым. Берём из руководства, каталога запчастей нет;
- ссылки на источники: документ и номер страницы PDF, не могут быть пустыми.

Сверх этого приложение хранит у себя номер TKT, время отправки, кто подтвердил и основание приоритета.

## 7. Стек и запуск

Стек решён 16.11: Python + Next.js. Библиотеки ниже окончательно выбираем в первый час спринта, когда увидим ТЗ и данные.

- **Сервер: Python 3.12, FastAPI.** Как и заглушки.
- **Руководства: PyMuPDF.** Для страниц-картинок Tesseract с русским языком.
- **Хранилище и поиск: предлагаю SQLite вместо PostgreSQL.** 6 PDF дают тысячи фрагментов, а не миллионы. Точный поиск (FTS5) встроен в Python, векторы лежат рядом. Это минус один контейнер, и запуск по README на Windows проще.
- **Эмбеддинги.** Локальная многоязычная модель (кандидат bge-m3, около 2,3 ГБ) или API. Закрытый контур не нужен, но локальная модель бесплатна и не зависит от сети. Скачать её можно заранее.
- **Интерфейс: Next.js**, сначала под телефон, с потоковым выводом ответов.
- **Модель: по API, через один слой.** Кандидаты: Claude Sonnet 5.5 и GigaChat Max. Выбираем в первые часы по проверочным вопросам: точность ссылок важнее цены. Для внедрения в России аргумент за GigaChat, поэтому его стоимость считаем в любом случае.
- **Без тяжёлых агентных фреймворков.** Цикл с инструментами из SDK провайдера.
- **Запуск по README под Windows 11:** две заглушки, наш сервер, интерфейс.

Стенд:

- **Где.** VPS с публичным адресом и HTTPS. На нём всё вместе: наш сервер, интерфейс и обе заглушки. Заглушки отдаём только нашему серверу, наружу смотрит один адрес.
- **Как ставим.** docker-compose: сервер, интерфейс, две заглушки и Caddy для HTTPS. Обновление стенда одной командой после пуша.
- **Модель и регион.** Claude API не работает с российских адресов, поэтому с Claude нужен зарубежный VPS. GigaChat работает и с российского. Регион выбираем вместе с моделью.
- **Память сервера.** С локальной bge-m3 нужно от 4 ГБ, с эмбеддингами по API хватит 2 ГБ.
- **Защита от расходов.** Ссылку увидят жюри и, возможно, другие. Ставим месячный лимит расходов у провайдера модели и ограничение частоты запросов на стенде. Без входа по паролю: жюри должно открыть сразу.
- **Заявки.** ТОиР-заглушка теряет заявки при перезапуске, наш список заявок хранится в файле базы на диске стенда.
- **Срок.** Поднимаем черновой стенд к 24-му часу спринта, а не в конце. После 28.11 не трогаем до питча, только смотрим, что живой.

Окружение проверено 16.11. Есть Python 3.12 и 3.13, uv, Node 24, pnpm, git и Docker Desktop (12 ядер, 16 ГБ). Tesseract не установлен.

## 8. Экономика

Формула: стоимость проверки = входные токены × цена входа + выходные токены × цена выхода. Плюс фиксированная инфраструктура в месяц.

Предварительная оценка на одну проверку с отклонением (заменить замерами из журнала):

| Шаг | Вход, токенов | Выход, токенов |
|---|---|---|
| Разбор результата | 25 000 | 1 500 |
| Три уточняющих вопроса | 24 000 | 1 500 |
| Заявка | 8 000 | 1 000 |
| Итого | около 60 000 | около 4 000 |

Проверка с результатом "норма" или "сбой записи" стоит в разы меньше: поиск по руководствам не нужен.

| Модель | Цена | Проверка с отклонением |
|---|---|---|
| GigaChat Lite | 0,065 ₽ за 1000 токенов | около 4 ₽ |
| GigaChat Pro | 0,5 ₽ за 1000 токенов | около 32 ₽ |
| GigaChat Max | 0,65 ₽ за 1000 токенов | около 42 ₽ |
| Claude Haiku 5.5 | $0.10 / $0.50 за 1 млн (вход / выход) | около $0.008 |
| Claude Sonnet 5.5 | $2 / $10 за 1 млн | около $0.16 |
| Claude Opus 5.5 | $4 / $20 за 1 млн | около $0.32 |

Цены GigaChat взяты со страницы тарифов для юрлиц (обновлена 7.10.2026). Это синхронный режим, НДС включён, вход и выход стоят одинаково, минимальный платёж 600 ₽ в месяц. Цены Claude указаны по прайсу Anthropic на 03.11.2026, без НДС.

Шаблон расчёта от организаторов ("калькулятор экономики решения", xlsx) считает стоимость **одного запроса**. В нём строка на каждый шаг агента, который вызывает модель: модель, вызовов на запрос, токены на входе и выходе по замеру, цены за 1 млн токенов, валюта. Суммы в рублях без НДС, доллары по курсу ЦБ на 26.11.2026. Отсюда:

- журнал с первого дня пишет токены по каждому шагу агента и каждой модели, иначе шаблон не заполнить;
- цены GigaChat выше указаны с НДС, в шаблон пересчитываем без НДС, цену за 1000 токенов умножаем на 1000;
- "запрос" определяем как разбор одной проверки с отклонением, а вопрос в чате и заявку даём отдельными строками. В комментарии шаблона так и пишем, плюс ссылки на прайсы и затраты на стенд.

Индексация 6 PDF почти ничего не стоит: эмбеддинги GigaChat стоят 0,014 ₽ за 1000 токенов, локальная модель бесплатна.

Пример для питча на парке задачи (верхняя оценка):

- **Нагрузка.** 50 машин, проверка раз в неделю, около 217 проверок в месяц. Считаем, что каждая с отклонением.
- **Стоимость модели.** Около 9 100 ₽ в месяц на GigaChat Max или около $35 на Claude Sonnet 5.5.
- **Стоимость простоя.** Сутки простоя магистрального тягача — примерно 45–56 тыс. ₽ выручки при пробеге 500 км в сутки (пробег — наше допущение, в источниках его нет). Нижняя граница: средняя ставка 76,5 ₽/км в декабре 2025 года (платформа «Монополия») и рост на 15–20% в 2026 году. Верхняя: медианная ставка тентованных фур 112,5 ₽/км на 1 ноября 2026 года (Cargo.Run, +28,3% к октябрю 2025). Для МАЗ, Урал, ПАЗ и УАЗ из парка задачи оценку надо пересчитать.
- **Вывод.** Месяц работы агента на весь парк стоит меньше суток простоя одной машины.

Ставки сверены по статьям 27.11.2026, источники в разделе 14.

Что снижает стоимость:

- **Повторное использование разбора.** Пар "тип неисправности + двигатель" всего 56 (14 типов на 4 семейства двигателей). Поиск по руководствам для пары делается один раз, дальше берётся готовый.
- **Кэширование неизменной части запроса:** инструкции и описания инструментов.
- **Простая модель на поиск и переформулировку,** сильная только на итоговый ответ.

Стоимость внедрения по этапам: подключение к ML-сервису заказчика, загрузка руководств его парка, адаптер к его ТОиР, развёртывание, пилот на одной колонне.

## 9. Как закрываем шесть критериев жюри

| Критерий | Что даёт 3 балла | Наш ответ |
|---|---|---|
| Соответствие задаче | Полное соответствие и нефункциональные требования | Пять пунктов задачи и три обязательных сценария видео. Работа с телефона. Контрольные случаи из раздела 3 проходят |
| Корректность реализации | Лучшие практики | Ссылки проверяются кодом по странице PDF, чужие руководства недоступны поиску, отправка только после подтверждения, проверочный набор вопросов с метриками |
| Потенциал внедрения | Готов к пилоту | Клиенты ML и ТОиР с понятными контрактами, запуск по README, сменная модель, свой список заявок |
| Степень готовности | Полнофункциональный продукт | Весь путь от выбора машины до номера TKT работает в одном видео без склеек |
| Агентность | Автономный многошаговый агент или память и оркестрация | После одной кнопки агент сам выбирает ветку, ищет, открывает страницы и предлагает приоритет. Память по машине, подтверждение человеком |
| Экономика | Обосновано для промышленной эксплуатации | Замеренная стоимость проверки на экране, расчёт на парк задачи, повторное использование разборов |

Сверх шести критериев: с 25.11 заказчик после питчей может выбрать одно решение для пилота, оно получает +6 баллов. Это как два критерия на максимуме. Поэтому в питче отдельно показываем, что нужно для пилота у заказчика и сколько он займёт.

## 10. Сценарий демо (до 3 минут, один дубль)

Организаторы требуют показать три сценария: отклонение с объяснением риска и ссылками на страницы, затем заявку; ответ на вопрос механика по базе знаний; сбой записи.

| Время | Что на экране |
|---|---|
| 0:00–0:10 | Одна фраза о задаче. Список парка |
| 0:10–0:50 | Сценарий 1. Машина с отклонением, кнопка "Получить результат диагностики". Видны шаги агента. Разбор: чем грозит, приоритет с основанием, порядок проверки со страницами. Нажатие на ссылку открывает страницу PDF с подсветкой |
| 0:50–1:25 | Сценарий 2. Вопрос про норматив, ответ со страницей. Вопрос, ответа на который в руководстве нет: агент честно говорит, что не нашёл |
| 1:25–2:00 | Сценарий 1, продолжение. "Оформи заявку": состав, подтверждение, номер TKT |
| 2:00–2:35 | Сценарий 3. Другая машина, сбой записи. Агент не ставит диагноз и просит повторить запись. Заявки нет |
| 2:35–2:55 | Стоимость и время этой проверки, история машины |
| 2:55–3:00 | Итог одной фразой |

С 25.11 ожидание ответа модели в видео можно ускорять. Вырезать, склеивать, подменять фрагменты и добавлять эффекты по-прежнему нельзя. Так что задержки ответа больше не главный риск, но потоковый вывод и прогретые сервисы всё равно нужны: на питче показываем вживую на стенде, а жюри задаёт свои вопросы. Видео пишем со стенда, а не с локальной машины, заодно это проверка стенда.
