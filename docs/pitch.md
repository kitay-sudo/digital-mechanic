# Сдача и питч: заготовки

Здесь только структура и тезисы. Цифры в квадратных скобках заполняем в спринте по замерам.

С 25.11 одностраничника нет: решение сдаётся формой в личном кабинете до 10:00 28.11. Ответы в форме короткие, поэтому тезисы ниже берём оттуда и сокращаем.

## Что приложить к форме

1. Ссылка на видео (до 3 минут, одним фрагментом, ожидание модели можно ускорить).
2. HTTPS-ссылка на открытый репозиторий с историей коммитов. Оценивают последний коммит до 10:00 28.11.
3. URL стенда. Стенд живёт до 23:59 3.12.
4. Ссылка на заполненный шаблон расчёта стоимости одного запроса, доступная без входа в аккаунт.
5. По желанию: папка в облаке с доп. материалами (скриншоты, проверочный набор вопросов с результатами, этот макет).

## Ответы для формы

Форма спрашивает: что сделано за 48 часов и что нет, подход и архитектура, стек и модели, запуск и поставка. Ниже заготовки под эти вопросы и под то, что стоит сказать сверх них.

**Задача и результат.**
Механик получает от ML-сервиса результат акустической проверки двигателя: код неисправности, оценку и уверенность. Сам по себе он ему мало что говорит. Агент превращает его в объяснение со ссылками на страницы руководства именно этого двигателя и по подтверждению оформляет заявку в ТОиР. Все пять требований задачи реализованы: [да / какие нет]. Контрольные случаи (сбой записи, помехи, нет инструкции в руководстве) отрабатываются: [да / какие нет].

**Подход и архитектура.**
Справочник парка, клиенты ML и ТОиР, индекс руководств с привязкой к страницам PDF, агент с инструментами, журнал стоимости. Проверки в коде: поиск видит только руководства двигателя этой машины, каждая ссылка сверяется со страницей, заявка не уходит без подтверждения и без источников.

**Стек и модели.**
Python, FastAPI, Next.js, [SQLite или PostgreSQL], PyMuPDF, Tesseract, [модель], [эмбеддинги]. Провайдер модели меняется в одном месте. Сторонние библиотеки, модели и API, вошедшие в продукт, перечисляем с лицензиями (п. 4.8).

**Принцип работы (в подход или отдельно).**
Механик выбирает машину и нажимает одну кнопку. Дальше агент сам: берёт результат, выбирает ветку по статусу и качеству записи, ищет в руководствах, предлагает приоритет с основанием. Потом диалог с источниками, черновик заявки, подтверждение. Память по машине учитывает повторы.

**Запуск и поставка.**

**Стоимость внедрения (для питча и выбора заказчика).**

## Питч на финале (5 минут + 5 минут вопросы, 1–3 декабря)

Показ только вживую на стенде: видео и презентация его не заменяют. После питчей заказчик может выбрать одно решение для пилота, это +6 баллов. Поэтому последний блок питча работает на этот выбор.

| Время | Блок | Тезис |
|---|---|---|
| 0:00–0:30 | Проблема | Парк узнаёт о поломке, когда машина встала. ML-сервис износ слышит, но механику нужен ответ по его двигателю, а не код F03 |
| 0:30–0:45 | Решение | Одна фраза: агент объясняет результат проверки, отвечает по руководству со страницей PDF и оформляет заявку |
| 0:45–3:00 | Показ на стенде | Три сценария: отклонение и заявка, вопрос по руководству, сбой записи. Если жюри спросит своё, отвечаем вживую |
| 3:00–3:45 | Внедрение | Два клиента с контрактами, запуск одной командой, модель меняется в одном месте |
| 3:45–4:30 | Экономика | Стоимость запроса по замеру, месяц парка против суток простоя |
| 4:30–5:00 | Пилот | Пилот у заказчика: срок, что от него нужно (доступ к ML-сервису, PDF его парка, API ТОиР), как измеряем успех |

Перед питчем: стенд проверен в день питча, ключ модели с запасом по лимиту, ссылка на стенд открыта во вкладке, видео открыто на случай обрыва связи.

## Вероятные вопросы жюри

**Что если ML-сервис ошибся?**
Агент не ставит диагноз сам. Низкую уверенность он показывает явно и предлагает проверки по руководству. Решение и подтверждение всегда за механиком.

**Как вы боретесь с выдуманными нормативами?**
Поиск видит только руководства двигателя выбранной машины, чужой PDF агенту просто недоступен. Каждое число из ответа код ищет на указанной странице PDF. Если не нашёл, ответ не показывается. Плюс проверочный набор вопросов по каждому руководству: [точность ссылок по замеру].

**Что если в руководстве нет инструкции по этой неисправности?**
Агент так и говорит и рекомендует дефектовку. Если есть общая процедура осмотра узла, ссылается на неё со страницей. Если нет ничего, заявка не уходит: без источника её отправить нельзя.

**Как считается приоритет?**
По оценке отклонения, уверенности модели, качеству записи и повторам в истории машины. Основание показано механику одной строкой. Пороги выставлены по данным задачи: [значения].

**Можно ли это в закрытом контуре?**
Да. Провайдер модели меняется в одном месте, эмбеддинги можно считать локально. Стоимость на GigaChat посчитана.

**Как подключить к нашей ТОиР?**
Заявка хранится в структурированном виде, клиент ТОиР переводит её в формат системы. Сейчас он работает с заглушкой по контракту из ТЗ. Для реальной системы нужны описание API или формат импорта.

**Почему это агент, а не чат-бот?**
После одной кнопки агент сам выбирает ветку по статусу и качеству записи, решает, что искать и какие страницы открыть, предлагает приоритет, помнит историю машины. Во внешней системе действует только после подтверждения человеком.

**Как обновлять руководства?**
Загрузка нового документа переиндексирует его. Ответы ссылаются на конкретную версию.
