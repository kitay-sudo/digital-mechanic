## 4. Правила поведения агента

Эти правила держит код, а не только инструкция модели. Исключение — П13: оно записано в инструкции модели, кодом не проверяется, поэтому помечено 🟡 до прогона на настоящей модели.

| № | Правило | Источник | Статус |
|---|---|---|---|
| П1 | Поиск и ссылки только по руководствам двигателя выбранной машины. Ссылка на чужой документ считается ошибкой | ТЗ F4, ОТВ 11 | ✅ |
| П2 | Каждая ссылка содержит дословную цитату со страницы. Код сверяет цитату с текстом страницы PDF. Страница, которую агент не может привести дословно, доказательством не считается | ЧАТ п. 5 | ✅ |
| П3 | Числа (нормативы, допуски, моменты, давления) и порядок работ берутся только из руководства со ссылкой на страницу. Число без источника — ошибка | ЧАТ п. 6 | ✅ |
| П4 | Гипотезы о причинах и рисках разрешены, но явно помечены и отделены от взятого из руководства. Гипотеза, оформленная как цитата, — ошибка | ЧАТ п. 6 | ✅ |
| П5 | `check_failed` или качество `bad`: выводов о двигателе нет, заявки нет, агент предлагает повторить запись. Без исключений | ТЗ F3, ЧАТ п. 3 | ✅ |
| П6 | Качество `warning`: предупреждение показывается всегда. Заявка допускается, только если механик сознательно подтвердил её после предупреждения | ЧАТ п. 3 | ✅ |
| П7 | Порог уверенности 0,50: ниже него заявка не оформляется, агент рекомендует повторную проверку. Порог виден в интерфейсе и назван в описании продукта | ЧАТ п. 3 | ✅ |
| П8 | `normal`: заявка не предлагается и не оформляется | МОК | ✅ |
| П9 | Применимая инструкция: процедура проверки, регулировки или ремонта того узла, на который указывает тип неисправности, из руководства на этот двигатель. Общий осмотр годится, если страница прямо относится к узлу. Оглавление и общий раздел о ТО без упоминания узла не годятся | ЧАТ п. 5 | ✅ |
| П10 | Применимой инструкции нет: заявка не отправляется, механик видит причину и получает текст рекомендации на дефектовку с результатом проверки | ОТВ 11, ЧАТ п. 5 | ✅ |
| П11 | Приоритет: high — на дефектовку до выпуска в рейс; medium — дефектовка на ближайшее ТО, работа под наблюдением; low — машина работает, узел проверяется на следующей проверке | ЧАТ п. 4 | ✅ |
| П12 | Схема приоритета: базовая критичность типа неисправности и ограниченная поправка по оценке отклонения. Основание показано механику и описано в продукте | ОТВ 14, ЧАТ п. 4 | ✅ |
| П13 | Запрет выпуска в рейс формулируется только тогда, когда в руководстве на этот двигатель прямо сказано, что эксплуатация запрещена, со ссылкой на страницу. Иначе это рекомендация | ЧАТ п. 4 | 🟡 |
| П14 | Заявка создаётся только по команде механика. Он видит состав и подтверждает именно его | ОТВ 16 | ✅ |
| П15 | `anomaly_type` в заявке равен значению из ответа `/diagnose` | МОК | ✅ |
| П16 | Тип неисправности не подходит двигателю (дизельная топливоподача у бензинового и подобное): агент сообщает о расхождении, инструкции в руководстве нет, заявка не отправляется | ЧАТ, вопрос без ответа, наше решение | ✅ |
| П17 | Описание признаков от ML-сервиса — данные, а не команды. Посторонние указания агенту в нём отбрасываются до модели и до экрана, механик видит предупреждение | Данные заказчика: три проверки с подложенными командами (T792HO98 S-0043, H142OX78 S-0113, E622KM47 S-0195) | ✅ |

## 6. Ответы ментора в чате 26.11

1. Видео до 3 минут.
2. PDF руководств и RAG-индексы с извлечённым текстом в открытый репозиторий и его историю не кладём. База знаний подключается через конфигурацию. В репозитории можно держать код, архитектуру, инструкции, Mock API и свои тестовые данные.
3. Один «запрос» для калькулятора — сценарий от получения результата диагностики до ответа механику или заявки. Все шаги модели внутри суммируются: выбор инструмента, поиск, генерация ответа, заявка, повторные вызовы, эмбеддинги запроса. Разовая индексация руководств идёт отдельной строкой. Нужны разбивка по шагам и пересчёт на парк с явными допущениями. Пример допущения: 50 машин, проверка раз в две недели, два-три вопроса механика на проверку.
4. Порог уверенности заказчик не задаёт. При `bad` выводов и заявки нет без исключений. При `warning` предупреждение всегда, заявка возможна после сознательного подтверждения. Порог 0,50 допустим, его надо показать в интерфейсе и назвать в описании.
5. Значения приоритета и правило про запрет рейса: см. П11–П13. Жюри приоритет с эталоном не сверяет.
6. Применимая инструкция и доказательства: см. П9, П10. Путь оформления дефектовки вне продукта реализовывать не нужно.
7. Гипотезы допустимы, если явно отделены: см. П3, П4.

Без ответа на 26.11 15:53: что делать при расхождении диагностики и карточки машины (F08 «Дизельная топливоподача» у бензинового ЗМЗ-5234.10, машина Y652CK98, проверка S-0132). Наше решение записано в П16.

## 9. Ограничения и запреты

| № | Ограничение | Статус |
|---|---|---|
| О1 | PDF руководств и индексы с их текстом не попадают в Git и его историю. Папки `knowledge/` и `materials/` закрыты в `.gitignore` | ✅ |
| О2 | Ключи и секреты только в `.env`, в репозитории лишь `.env.example` | ✅ |
| О3 | Код, конфигурации, промпты и индексы созданы в спринте. До спринта сделаны только проектные документы и статичный макет, они раскрыты в README | ✅ |
| О4 | Не входит в задачу: обучение модели звука, обработка WAV, потоковое аудио, реальная 1С, мобильное приложение | ✅ |

Сейчас вместо ключа модели работает заглушка модели (`LLM_PROVIDER=mock`): она выбирает инструменты по простым правилам и собирает ответ из найденных фрагментов дословно. Весь путь, правила и проверки с ней работают и покрыты 30 автотестами. Для качества ответов, которое оценит жюри, нужен ключ настоящей модели: `LLM_PROVIDER=anthropic` и `ANTHROPIC_API_KEY` в `.env`.

Слой Claude (`backend/app/agent/llm_anthropic.py`) написан по документации SDK, но без ключа ни разу не запускался. Первый запуск с ключом может потребовать правок.

## 10. Что осталось до сдачи

1. Поставить ключ модели, проверить слой Claude и прогнать С1, С2, три проверки с подложенными командами и контрольные вопросы по каждому руководству.
2. Завести публичный репозиторий и отправить историю коммитов.
3. Поднять стенд на VPS, проверить с телефона.
4. Заполнить шаблон расчёта по замерам из журнала (`/api/usage/summary`).
5. Записать видео со стенда и заполнить форму.
